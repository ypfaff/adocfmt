= Formatting rules
:toc:

adocfmt applies the rules on this page and leaves the rest of the document as it is.

== Guarantees

* A byte that no rule covers is written back unchanged.
* Line endings keep their form, so a file written with Windows line endings keeps them, and a line a rule writes ends the same way.
* Front matter is left alone, the block of YAML that some static site generators put at the top of a file.
* Lines whose meaning depends on an https://docs.asciidoctor.org/asciidoc/latest/directives/include/[include] or a https://docs.asciidoctor.org/asciidoc/latest/directives/conditionals/[conditional] are left alone, because what they hold is known only once Asciidoctor has resolved the directive.
* A document that cannot be read reliably is refused: adocfmt reports what it found and writes nothing.
* No rule changes what the rendered document shows.
Asciidoctor decides what a document means, and link:testing-strategy.adoc[the testing strategy] describes how every rule is checked against it.

[#trailing-whitespace]
== Trailing whitespace

Spaces and tabs at the end of a line are removed, including inside code and literal blocks.
A line that holds nothing but whitespace becomes empty.

`·` marks a space.

[cols="1,1"]
|===
| Before | After

a|
....
Text.··
line +··
....
a|
....
Text.
line +
....
|===

AsciiDoc forces a https://docs.asciidoctor.org/asciidoc/latest/blocks/hard-line-breaks/[line break] by ending a line with a space and a `{plus}`.
That space is part of the break and stays; only the whitespace after the `{plus}` is removed.

[#heading-markers]
== Heading markers

A one-line https://docs.asciidoctor.org/asciidoc/latest/sections/titles-and-levels/[section title] is written with `=` signs and a single space.
A closing marker at the end of the line is removed.

[cols="1,1"]
|===
| Before | After

a|
....
## Section ##
==   Other
....
a|
....
== Section
== Other
....
|===

The https://docs.asciidoctor.org/asciidoc/latest/document/header/[document title] is written the same way, and the author, revision and attribute lines below it stay as they are.

Left alone:

* A document title written on two lines.
It turns on https://docs.asciidoctor.org/asciidoctor/latest/migrate/asciidoc-py/#compatibility-mode[compat-mode], and the same document on one line would render its inline markup differently.
* A title the rewrite would change.
A closing marker counts only when it matches the one in front of it, so `## Title ==` has the title `Title ==`, while `== Title ==` would have the title `Title`.

[#setext-headings]
== Setext headings

A section title written as a line of text with an underline below it moves onto one line.

[cols="1,1"]
|===
| Before | After

a|
....
Section
-------
....
a|
....
== Section
....
|===

The underline character sets the level: `=` is level 0, `-` is level 1, `~` is level 2, `^` is level 3, and `{plus}` is level 4.

Left alone:

* An indented title.
A one-line title cannot carry the indentation, because Asciidoctor skips the whitespace between the marker and the title.
* A two-line title at the very top of a document.
That one is the document title rather than a section title, and it stays on two lines; see <<heading-markers>>.

[#blank-lines]
== Blank lines

One blank line separates two blocks, and none binds a metadata line to its block or one list item to the next.
The file starts with no blank line and ends with a single line ending.

[cols="1,1"]
|===
| Before | After

a|
....
= Title
:toc:

== Section
.Listing

----
code
----
text



* one

* two
....
a|
....
= Title
:toc:

== Section

.Listing
----
code
----

text

* one
* two
....
|===

Asciidoctor renders a block the same with and without a blank line in front of it, which is what makes the separating line free to insert.
In a few places a blank line is syntax rather than spacing, and there adocfmt keeps what it finds.

Left alone:

* Blank lines inside a list item.
One there decides what still belongs to the item, so adocfmt neither adds nor removes one.
+
.Where the note ends up
[%collapsible]
====
[cols="1,1"]
|===
| Part of the item | A block of its own

a|
....
* An item
+
----
code <1>
----
<1> a note
....
a|
....
* An item
+
----
code <1>
----

<1> a note
....
|===
====
* The blank line after an item that ends in indented text.
Indented text runs on to the next blank line, so without it the marker of the next item is read as part of that text.
+
.Where the second item ends up
[%collapsible]
====
[cols="1,1"]
|===
| Inside the indented text | An item of its own

a|
....
* one

  indented text
* two
....
a|
....
* one

  indented text

* two
....
|===
====
* The blank lines around a lone `+`.
The run above it picks which list level the block below attaches to, the run under it whether that block attaches at all: at most one blank line attaches it, two or more end the list.
Outside a list the `+` attaches nothing, and Asciidoctor reads it and everything under it down to the next blank line as one paragraph.
+
.What a lone `+` joins
[%collapsible]
====
[cols="1,1"]
|===
| One paragraph | Two paragraphs

a|
....
Text.

+
More text.
....
a|
....
Text.

+

More text.
....
|===
====
* The blank line under a comment.
Asciidoctor throws comments away before it renders, so nothing ties a comment to the block beneath it, and pulling it down would only change how the source reads.
* The blank line under an attribute entry whose last line still ends in `{backslash}` or `{plus}`.
The value reads on to the next blank line, so removing that line would feed the block below into the attribute instead of rendering it.
* Whatever stands under front matter, down to the first blank line.
Asciidoctor does not skip front matter unless it is told to, and reads everything from the opening fence to that blank line as one paragraph, so a blank line there changes what the document title below it becomes.
+
.What the title below front matter becomes
[%collapsible]
====
[cols="1,1"]
|===
| Read as text | A section title

a|
....
---
layout: post
---
= Title
....
a|
....
---
layout: post
---

= Title
....
|===
====
* A blank line at the top of a file whose first line of content is a `---` that a later `---` closes.
Front matter counts only when the fence is the very first line, so removing that blank line would make front matter out of lines that are none.
* Blank lines next to an include or a conditional, and the ones inside a block whose content one of them decides.
* Blank lines inside a listing, a literal block or a table, which count as one block each.

[#block-delimiters]
== Block delimiters

The two lines fencing a https://docs.asciidoctor.org/asciidoc/latest/blocks/delimited/[delimited block] are written as short as the block allows, which is four characters wherever no line inside asks for more.

[cols="1,1"]
|===
| Before | After

a|
....
--------
code
--------
....
a|
....
----
code
----
....
|===

A table is fenced the same way, except that its first character picks https://docs.asciidoctor.org/asciidoc/latest/tables/data-format/[how the rows are read] and therefore stays: `{vbar}=======` becomes `{vbar}===`, and `,=======` becomes `,===`.

A block closes on a line equal to the one that opened it, so a fence may only shrink to a width no line inside the block ends up with.

[cols="1,1"]
|===
| Before | After

a|
....
--------
----
code
--------
....
a|
....
-----
----
code
-----
....
|===

A line counts however deep inside the block it sits, because Asciidoctor carries the closing line of a block into the blocks nested in it.

.Where a line inside a nested block ends the block around it
[%collapsible]
=======
The `====` sits in a listing, and closes the example block around it all the same.
The fence of that example block therefore stops at five characters rather than four.

[cols="1,1"]
|===
| Before | After

a|
....
======
----
====
----
======
....
a|
....
=====
----
====
----
=====
....
|===
=======

Left alone:

* An https://docs.asciidoctor.org/asciidoc/latest/blocks/open-blocks/[open block] and a Markdown fence.
Each has one legal width, two dashes and three backticks, so there is nothing to shorten.
* A https://docs.asciidoctor.org/asciidoc/latest/comments/[comment block].
It is a block of its own only where it stands alone, and part of the metadata of the block below it otherwise, so rewriting it would turn on where it sits rather than on what it holds.
* A block an include or a conditional reaches, inside its body or on the line above it.
What the directive brings in may hold the very line a shorter fence would close on.
